# Kindle dashboard prior art

**Research snapshot: 2026-10-21.** GitHub stars and latest commit dates below are the values visible on the linked repository/history pages at the time checked; they can change. This survey favors project READMEs, source files, commit histories and license files, plus official Amazon and KindleModding sources. `Not stated` / `[unverified]` means I could not confirm the point in the project’s own published sources; do not treat it as compatibility or a no-key guarantee. KindleModding device aliases are explained in the [official model catalog](https://kindlemodding.org/models.json).

## Recommendation for rekindle

Start by identifying the Kindle’s exact model (serial prefix) and firmware; that determines whether the stock-browser route or a jailbreak-based implementation is practical. KindleModding’s [official jailbreak wizard](https://kindlemodding.org/jailbreak-wizard.html) asks for model/serial, firmware, registration and ad status for this reason.

1. **[pascalw/kindle-dash](https://github.com/pascalw/kindle-dash)** — Best first low-power reference: server-produced image, simple device-side fetch/`eips`, and suspend-until-update design. It is explicitly tested on Kindle 4 NT, requires jailbreak, and is older, so port to the actual target rather than assuming compatibility.
2. **[higoorc/kindle-dash](https://github.com/higoorc/kindle-dash)** — Strong Home Assistant pattern: an on-device browser dashboard backed by a local proxy, with deep sleep and RTC wake. The README’s device evidence is an older Paperwhite 1 on 5.3.x, and its “weeks” battery statement is an author claim, not a measured benchmark.
3. **[sibbl/hass-lovelace-kindle-screensaver](https://github.com/sibbl/hass-lovelace-kindle-screensaver)** — Most direct reuse if the household already uses Home Assistant: render an existing Lovelace view to an image and have the Kindle-side Online Screensaver fetch it; conditional requests avoid redraw/download when content is unchanged. Requires jailbreak and an HA access token.
4. **[GuoBug/kindle-weather-station](https://github.com/GuoBug/kindle-weather-station)** — Good on-device-rendering reference for a clock/weather screen, touch controls and an explicit eco mode; the README says it supports several touch Kindles, but it requires jailbreak, Python/Pillow and an OpenWeatherMap key.
5. **[matopeto/kindle-weather-dashboard](https://github.com/matopeto/kindle-weather-dashboard)** — Best no-jailbreak/stock-browser starting point in this set: a static browser page tested on Kindle 3/4/5 and Paperwhite 3. It uses an OpenWeatherMap key, and leaving a browser page continuously awake is a separate power-management problem.

These are architectural starting points, not a combined implementation recommendation. Avoid committing to the device-side architecture until the target model and firmware are known.

## Architectural tradeoffs

### Server-rendered image, fetched or polled by Kindle

This covers `pascalw/kindle-dash`, `mpetroff/kindle-weather-display`, `sibbl/hass-lovelace-kindle-screensaver`, `abbymartin/eink-dashboard`, `danielktaylor/kindle-weather-dashboard`, and both TRMNL integrations. The server can use normal web stacks, weather APIs, calendars and layout tools, then send a fixed-size grayscale image; device-side work stays small (`wget`/HTTP plus `eips`, FBInk, Online Screensaver, or a KOReader plugin). It is a strong fit for an always-present dashboard and avoids relying on the Kindle’s old browser renderer. Conditional image fetches and stable image hashing can avoid needless screen updates ([sibbl](https://github.com/sibbl/hass-lovelace-kindle-screensaver), [Kuuhhl](https://github.com/Kuuhhl/onlineScreensaver)).

Tradeoffs: a server or cloud endpoint must stay available; the Kindle needs connectivity when it refreshes; and truly low-power operation depends on a working device-side suspend/wake loop, not just static e-ink. Some examples are simple shell programs; others depend on HA, Docker, browser automation or an Online Screensaver install. “Pull” is typical: the Kindle polls/fetches a server-generated image. A remote renderer does not itself mean the device receives a true push notification.

### Browser page rendered on the Kindle

`matopeto`, `niutech`, `sssssea7`, `toddsherman` and `dinesh-it` keep layout/data presentation in a web page. This minimizes deployment friction and can avoid jailbreak when using the stock Experimental Browser; a hosted page can be changed without USB/SSH access. It is the most convenient path for a quick proof of concept when a compatible stock browser is available ([Amazon Paperwhite 2 manual](https://kindle.s3.amazonaws.com/UserGuide/Paperwhite_V2/Kindle_Paperwhite_V2_UserGuide_US.pdf), [niutech README](https://github.com/niutech/kindle-dashboard/blob/master/README.md), [matopeto README](https://github.com/matopeto/kindle-weather-dashboard/blob/master/README.md)).

Tradeoffs: Kindle browser versions are old and model-specific; modern JS/CSS or remote assets may fail. A normal page’s refresh timer does not solve browser session persistence or sleep. Continuous display commonly relies on debug/undocumented screensaver commands or wall power, and device/firmware behavior is not guaranteed by Amazon’s manual. A no-jailbreak browser route therefore trades implementation simplicity for less reliable kiosk behavior and more active power use.

### On-device framebuffer drawing

`GuoBug/kindle-weather-station` and `Invictus596/Kindle-Dashboard` draw locally with Python and display through the Kindle’s framebuffer tools. This bypasses the browser and can give the author exact control over font/layout/refresh cadence; `GuoBug` also demonstrates explicit touch controls and eco/performance modes.

Tradeoffs: jailbreak, shell access and compatible Python/Pillow or Entware packages are prerequisites; code and network/API integration must match the device. Directly keeping the device awake is straightforward but can dominate battery use, and these projects do not show a generic supported RTC/suspend scheme.

### KOReader plugin

`MarinaHampton/kindle-dashboard`, TRMNL’s `trmnl-koreader`, `WeatherLockscreen` and `weather.koplugin` use KOReader’s Lua/plugin environment. This can offer a natural fit for sleeping/lockscreen behavior and easy access to KOReader rendering. `WeatherLockscreen` is the clearest example of waking briefly for weather then returning to sleep; TRMNL’s plugin can fetch a server-rendered dashboard.

Tradeoffs: Kindle users still need a jailbreak and KOReader installation; model compatibility and plugin behavior vary. Some plugins are only weather data views rather than full household dashboards, while service-backed options such as TRMNL add account/server dependencies.

Coverage facts above link to the live [compatibility JSON](https://kindlemodding.org/jailbreaks.json); method descriptions and constraints are on the official [WinterBreak2](https://kindlemodding.org/jailbreaking/WinterBreak2/), [WinterBreak](https://kindlemodding.org/jailbreaking/WinterBreak/), [SpringBreak](https://kindlemodding.org/jailbreaking/SpringBreak/), [AdBreak](https://kindlemodding.org/jailbreaking/AdBreak/) guides and [FAQ](https://kindlemodding.org/jailbreaking/jailbreak-faq.html). **SpringBreak source mismatch:** its GitHub [README](https://github.com/KindleModding/SpringBreak/blob/main/README.md) says KT5/PW5 on 5.19.2+ and KT4/PW4 on 5.18.1.1.1, while the official JSON lists KT5/PW5 through 5.19.2.0.1 and KT4/PW4 from 5.18.1. Do not resolve that discrepancy by guessing; check the wizard and current guide for the exact device. The official FAQ also says stock firmware cannot be downgraded after an update, and warns jailbreak extensions may be affected by firmware changes.

### Non-jailbreak stock Experimental Browser

Amazon’s [Paperwhite 2 user guide](https://kindle.s3.amazonaws.com/UserGuide/Paperwhite_V2/Kindle_Paperwhite_V2_UserGuide_US.pdf) documents an Experimental Browser with Wi-Fi, JavaScript, SSL and cookies. It is a browser, not a documented kiosk/auto-refresh service: the guide documents normal idle sleep and a screensaver, not a supported way to pin a dashboard open. Projects such as [niutech](https://github.com/niutech/kindle-dashboard/blob/master/README.md), [matopeto](https://github.com/matopeto/kindle-weather-dashboard/blob/master/README.md) and [sssssea7](https://github.com/sssssea7/KindleDashboard/blob/main/README.md) show that static/refreshing pages can be opened there. Their continuous-view approach depends on page timers and/or model/firmware-dependent sleep controls; it should not be treated as a guaranteed stock feature. If preserving stock firmware is the priority, test the exact Kindle/firmware in person and expect that plugged-in operation may be needed.

Amazon’s manual says the static screensaver itself uses no power; this does not mean Wi-Fi, CPU, frontlight or keeping the Kindle awake are power-free. For a battery-oriented installation, prefer a tested suspend-and-wake implementation over simply increasing browser refresh frequency.
